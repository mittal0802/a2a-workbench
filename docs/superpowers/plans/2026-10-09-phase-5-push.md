# Phase 5 — Push notifications: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Manage an agent's push notification configs (Create/Get/List/Delete, A2A §3.1.7–§3.1.10) through the official SDK, receive the agent's webhook POSTs in a built-in receiver that validates them as A2A §4.3.3 and §13.2 require, and show every delivery in the chat and a Notifications inbox — in web, CLI and MCP.

**Architecture:** `core/push/` holds `PushService` (SDK push-config calls with the agent's auth, recorded like other calls), `HookStore` (Workbench webhooks: one per config, with a generated single-purpose token and Bearer credential stored as hashes), and `Receiver` (validates `Authorization`, the token, the body as an SDK `StreamResponse`, and that the task id is the expected one; stores a `PushDelivery`; emits a `push` timeline event into the conversation owning the task; publishes on `push:<agent_id>`). `SendOptions.push` attaches a Workbench webhook inline (`SendMessageConfiguration.task_push_notification_config`, §3.2.2). The public base URL is `PUBLIC_BASE_URL`, a `cloudflared` quick tunnel when requested, or the bind address. `/hooks/*` is exempt from the host guard (agents call it from anywhere) but always authenticated by the hook's credentials.

**Tech Stack:** a2a-sdk 1.2.2 client push methods and server `InMemoryPushNotificationConfigStore` / `BasePushNotificationSender` (zoo), FastAPI, SQLAlchemy, Typer, MCP, React.

**Spec:** `docs/superpowers/specs/2026-10-07-a2a-workbench-design.md` §3 row H, §5.4, §12 Phase 5. A2A: §3.1.7–§3.1.10, §3.2.2, §3.3.4, §4.3, §6.6, §13.2.

## Global Constraints

- Earlier phases' constraints apply (official SDK only, secrets via the vault/hashes and never logged, every surface, docstrings describe the function, no AI attribution).
- Webhook credentials are generated per config (`secrets.token_urlsafe(32)`), shown once to the caller of create (they go to the agent inside the config), and stored only as SHA-256 hashes; deliveries record headers with `Authorization` and the token masked.
- The receiver answers 2xx only to authentic, well-formed deliveries for the expected task (§4.3.3 MUST validate the task id; §13.2 MUST validate authenticity). Duplicates are acknowledged (2xx) and flagged (§4.3.3 SHOULD be idempotent). A per-hook rate limit (60/min) answers 429 (§13.2 SHOULD).
- A2A does not say how the config `token` is delivered. The SDK sends `X-A2A-Notification-Token`; the receiver checks it there, and a missing token is a note, not a failure. Logged in `docs/upstream-gaps.md`.
- The Workbench never sends push configs to agents that do not declare `capabilities.pushNotifications` without saying so: the UI warns, and the agent's `PushNotificationNotSupportedError` (§3.3.4) is shown as returned.

## Review Focus

1. **Forged delivery** (wrong/missing `Authorization`, other hook's token, unknown hook id): 401/404, stored as rejected with the reason, no timeline event. *Test:* Task 2 `test_unauthenticated_delivery_is_rejected`.
2. **Delivery for an unexpected task id:** rejected (400) with reason `unexpected_task`. *Test:* Task 2 `test_unexpected_task_is_rejected`.
3. **Inline config before the task exists:** the hook binds to the task id the agent returns, and later deliveries for it are accepted. *Test:* Task 3 `test_inline_push_binds_to_the_new_task`.
4. **Duplicate deliveries:** acknowledged, flagged `duplicate`, shown once in chat. *Test:* Task 2 `test_duplicate_delivery_is_acknowledged_and_flagged`.
5. **Secrets:** webhook credentials and tokens never appear in API responses (other than the one create response), deliveries, exchanges or logs. *Test:* Task 4 `test_push_secrets_are_masked`.

### Task 1: Zoo push support and PushService (config CRUD through the SDK)
Files: `fixtures/zoo.py` (push store + sender; `capabilities.push_notifications=True`), `core/push/__init__.py`, `core/push/service.py`; tests `tests/core/push/test_push_service.py`.
`PushService(agents, sink, auth)`: `create(agent_id, task_id, *, url, token=None, auth_scheme=None, auth_credentials=None) -> dict`, `get(agent_id, task_id, config_id)`, `list(agent_id, task_id, page_size=None, page_token=None) -> {"configs","next_page_token"}`, `delete(agent_id, task_id, config_id)`. Errors as `AgentCallError` (classified, auth-scrubbed).
Tests: CRUD round trip against the zoo for a working task; pagination; delete idempotent (§3.1.10); `PushNotificationNotSupported` from a zoo with push disabled; unknown task → TaskNotFound.

### Task 2: Hooks and the receiver
Files: `core/store/models.py` (`PushHook`, `PushDelivery`), `core/push/hooks.py`, `core/push/receiver.py`, `core/conversations/timeline.py` (`push` kind), `api/routes_hooks.py` (`POST /hooks/{hook_id}`), `api/host_guard.py` (exempt `/hooks/`); tests `tests/core/push/test_receiver.py`, `tests/api/test_hooks_api.py`.
`HookStore.create(agent_id, *, task_id=None, conversation_id=None) -> NewHook(id, url, token, auth_scheme="Bearer", credentials)`; `bind_task(hook_id, task_id)`; `get`, `list(agent_id)`, `delete`. `Receiver.receive(hook_id, headers, body) -> (status, PushDeliveryOut)` with verdict `accepted|rejected`, reasons, `duplicate`, parsed `kind` (task/message/status_update/artifact_update), task id, state.
Tests: accepted delivery creates a `push` event in the owning conversation; unauthenticated rejected; unexpected task rejected; duplicate flagged; malformed body 400; rate limit 429; token missing → note; deliveries never store secrets.

### Task 3: Inline push on send, public URL, tunnel
Files: `core/conversations/options.py` (`push: bool`), `core/conversations/service.py` (create hook, set `configuration.task_push_notification_config`, bind task id from the response), `core/config.py` (`public_base_url`), `core/push/tunnel.py` (cloudflared quick tunnel: start/stop/url), `core/workbench.py`.
Tests: `test_inline_push_binds_to_the_new_task` (send `long` with push=True and stream=False/return_immediately → deliveries arrive from the zoo and show as push events), public URL precedence, tunnel helper parses the trycloudflare URL from a fake process.

### Task 4: API, CLI, MCP
API: `GET/POST /api/agents/{id}/tasks/{task_id}/push-configs`, `GET/DELETE …/push-configs/{config_id}`, `GET /api/agents/{id}/push/deliveries`, `GET /api/push/deliveries/{id}`, `GET/PUT /api/settings/public-url`, `POST/DELETE /api/settings/tunnel`; WS topic `push:<agent_id>`. CLI: `push create <agent> <task> [--url --token --auth-scheme --auth-credentials | (default) Workbench webhook] [--json]`, `push get|list|delete`, `push deliveries <agent>`, `push listen <agent>`, `send --push`. MCP: `push_create`, `push_get`, `push_list`, `push_delete`, `push_deliveries`. Tests for each, plus `test_push_secrets_are_masked`.

### Task 5: Web
Notifications tab (task picker from Tasks, configs list with create — Workbench webhook by default or a custom URL/token/auth — get and delete; capability warning), deliveries inbox (live over WS: verdict, reasons, masked headers, payload JSON), push cards in chat turns, Options menu "Notify me by webhook (push)", Settings: public URL and tunnel. Tests for each.

### Task 6: E2E and docs
E2E: send `long` with push on → push cards appear in chat and in the inbox; create/delete a config in the Notifications tab. Docs: README push section, agents.md, upstream-gaps (token delivery header), spec §5.4 corrected to the SDK header.
